## Task 1 — design.md integration into live themes

### What design.md contains

`design.md` is a descriptive extraction of the v6 dashboard visual language: the PRD semantic token set (`--bg`, `--surface`, `--ink`, `--primary`, `--line`, `--nav`, `--gradient`) plus Manrope + DM Mono and compact density.

### PRD alignment check (04-theme-system.md)

The live engine already implements the PRD correctly:

- Colour tokens only change between themes; layout tokens are theme-invariant. ✅
- Light/dark variants per family; Liquid Onyx is Slate Navy's dark mode, not a separate theme. ✅
- Semantic tokens are generated by `prdSemanticTokens()` and set on `:root`. ✅
- `--gradient` keeps the 135-degree primary-to-secondary structure. ✅

The theme preference is user-scoped by design (`user_preferences` table). The task brief asked for tenant scoping. The PRD for theming does not mandate tenant scope, and the app comment states the user-scope decision explicitly. Per rule precedence (PRD over task note), the user scope is kept. Tenant-differentiated theming remains demonstrated in the prototypes (slide 5, v3/v4), not forced into the engine. This is the one deliberate deviation, recorded here.

### Conflict found and fixed

`Design.md` §3 records three coverage-note bridge tokens: `--bd-ink`, `--bd-ink-muted`, `--bd-ink-icon`. They existed only as hard aliases in `index.css` and were absent from `THEME_COLOR_TOKENS`. A theme could never override them, which contradicts the coverage note ("map to the existing semantic ink hierarchy" as theme-managed tokens).

Fix:

- Added `bd-ink`, `bd-ink-muted`, `bd-ink-icon` to `THEME_COLOR_TOKENS`.
- `buildBundle()` now emits them per family and per mode: `c.ink`, `c.ink2`, `c.primary`.

Dark variants flow through the same `buildBundle()`, so both modes receive correct values. The `index.css` aliases remain as fallback. No component changes needed.

### Contract test

`themePrdContract.test.js` locks: all 20 PRD semantic tokens exist on all 6 selectable families in light and dark; token sets match exactly between modes; the gradient keeps the 135-degree form; Slate Navy light equals `#f0f4f8`/`#1e3a5f` and dark equals `#0f172a`/`#60a5fa` (the locked palette); legacy presets stay unselectable.

## Task 3 — onboarding v3 and v4

Random draw from the live family library produced **Ocean Teal** (v3) and **Amber Terracotta** (v4).

Both files:

- Fork the manus v2 candidate: same 6-slide story arc, spring swipe engine, approval-gate auth flow, reduced-motion support, responsive mobile/fold/desktop tiers.
- Theme layer placed after a structural-only `:root` (safe areas, easings), mirroring `TEAL_LIGHT`/`TEAL_DARK` and `AMBER_LIGHT`/`AMBER_DARK` from `themePresets.ts` as HSL triplets in PRD token names. This demonstrates the theme system's flexibility: one structure, two complete colour identities.
- Light/dark mode via `html[data-theme]` per the PRD contract. A header toggle switches modes, persists to `localStorage`, seeds from `prefers-color-scheme`, and re-seeds on system change. The copied v2 `prefers-color-scheme` slate block was removed from both files so it cannot fight the `data-theme` system.
- Theme-tinted shadows per family (Design.md rule: shadows carry the primary hue).
- Status colours re-derived per family and per mode from `CoreColors` (`attention`, success, warning).
