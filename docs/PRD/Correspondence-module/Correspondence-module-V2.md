# PRD — Correspondence Module (Official Letters)

**Version:** 2.0
**Status:** Draft
**Module:** Correspondence / Official Letters
**Applies To:** BIGDROPS ERP

---

# 1. Overview

The Correspondence module enables users to create, manage, render, print, email, and archive professional business letters.

Unlike invoices or quotations, correspondence is document-centric rather than transactional.

The module must support:

- Manual authoring
- AI-assisted JSON import
- Rich text editing
- Professional PDF generation
- Professional Email rendering
- Plain text rendering
- Multiple reusable company letterhead templates

---

# 2. Goals

The module must:

- Produce high-quality business correspondence.
- Support reusable company branding.
- Remain portable.
- Separate document content from company assets.
- Support future multi-tenancy.
- Support future workflow approvals.

---

# 3. Non Goals

This PRD does NOT include:

- Email transport
- SMTP
- Microsoft Word import
- Markdown import
- OCR
- Audit workflow
- Approval workflow

---

# 4. Core Principle

The system separates:

## A. Document Content

Owned by the letter.

Examples:

- Subject
- Recipient
- Sender
- Rich text body

These travel with the document forever.

---

## B. Business Metadata

Owned by BIGDROPS.

Examples:

- Letter number
- Company profile
- Logo
- Representative
- Signature
- Stamp
- Audit trail

These are managed by the application.

---

# 5. Letter Structure

Every letter consists of:

- Header
- Subject
- Recipient
- Sender
- Rich body
- Attachments
- Signature
- Footer

---

# 6. JSON Import

JSON is the ONLY supported AI import format.

No Markdown import.

No DOCX import.

No HTML import.

---

## JSON imports ONLY:

- Subject
- Recipient
- Sender
- Rich body
- Formatting
- Attachment placeholders (optional)

---

## JSON MUST NEVER import:

- Letter number
- Date
- Company profile
- Client ID
- Company ID
- Logo
- Signature image
- Stamp
- Audit information
- Database IDs

---

# 7. Generated By BIGDROPS

After import (or manual creation), BIGDROPS generates:

- Letter Number
- Date
- Lifecycle state
- Audit metadata

---

# 8. Company Profile

A letter may optionally reference a saved Company Profile.

Selecting a profile automatically provides:

- Company name
- Address
- Phone
- Email
- Website
- Logo
- Default footer

Company assets are never imported by AI.

---

# 9. Representative

Representative is independent from Company Profile.

One company may have multiple representatives.

Each representative contains:

- Name
- Position
- Signature

Examples:

- Managing Director
- Project Engineer
- Business Development Manager
- Procurement Officer

Changing representative never changes company branding.

---

# 10. Signature

Signature images are never imported.

User chooses:

- No signature
- Saved signature
- Temporary uploaded signature

Signature rendering occurs only during document rendering.

---

# 11. Company Stamp

Stamp is never imported.

User chooses:

- None
- Official company stamp
- Custom uploaded stamp

Future versions may support multiple stamp presets.

---

# 12. Logo

Logo is never imported.

Logo appears automatically when a Company Profile is selected.

Manual sender mode does not automatically include a logo.

---

# 13. Recipient

Recipient supports:

## Manual

User enters:

- Company
- Contact
- Address

or

## Saved Client

Selecting a saved client copies current values into the document.

The saved client is NOT permanently linked.

Letters remain historically accurate even if the client later changes.

---

# 14. Sender

Sender supports:

## Manual

Free text.

or

## Company Profile

Copies company information into the document.

The representative remains independently selectable.

---

# 15. Rich Text

The editor supports:

- Bold
- Italic
- Underline
- Font family
- Font size
- Alignment
- Ordered lists
- Bullet lists
- Block quotes
- Horizontal rules
- Images
- Tables
- Page breaks (future)

The canonical storage format remains the LetterBody JSON schema.

HTML is never stored.

---

# 16. Images

Images are supported inside the body.

Images are referenced by asset IDs or URLs.

The JSON specifies where each image appears.

Example:

- Between paragraphs
- Full width
- Left aligned
- Right aligned
- Centered

Multiple images are supported.

---

# 17. Attachments

Attachments use the existing Cloudinary upload pipeline.

Supported examples:

- PDF
- Images
- Excel
- ZIP
- Word

Letters store attachment metadata only.

Renderer decides presentation.

Possible rendering:

- Appendix pages
- Download links
- Attachment section

---

# 18. Letter Templates

Rendering is template-driven.

Initial templates:

- Classic
- Corporate
- Government
- Minimal
- Legal
- Tender Submission

Changing templates never modifies document content.

Only presentation changes.

---

# 19. Rendering Targets

Every LetterDocument can render to:

- PDF
- Email HTML
- Plain Text

All renderers consume the same LetterDocument.

No renderer reads TipTap state.

No renderer reads HTML.

No renderer reads database rows.

---

# 20. JSON Schema Ownership

LetterBody JSON is the canonical source of truth.

Editor serializes into it.

Renderers consume it.

Import produces it.

Persistence stores it.

---

# 21. Future Multi-Tenancy

The module must isolate:

- Company Profiles
- Representatives
- Signatures
- Stamps
- Templates

per tenant.

Document content remains tenant-independent.

---

# 22. Acceptance Criteria

The module is complete when:

- Manual authoring works.
- JSON AI import works.
- Rich formatting persists.
- Multiple templates render correctly.
- Company branding is reusable.
- Representatives are selectable.
- Signatures render correctly.
- Stamps render correctly.
- Images render in their defined positions.
- Attachments upload using the existing Cloudinary pipeline.
- PDF rendering matches Email rendering.
- Plain text rendering preserves readable structure.
- Document content remains independent of application assets.
