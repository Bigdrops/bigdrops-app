## 1. Receipt Identity

A receipt is a legal proof-of-payment document. It records that a specific payment was received by a specific company from a specific client, against a specific invoice.

### 1.1 Identity Fields

Every receipt has an immutable identity established at creation:

```ts
interface ReceiptIdentity {
  id: string                    // UUID primary key
  receipt_number: string        // e.g. RCP-000001 (prefix engine)
  payment_id: string            // FK to payments table
  invoice_id: string            // FK to invoices table
  client_id: string             // FK to clients (denormalized snapshot)
  created_at: string            // timestamptz
}
```

### 1.2 Identity Immutability

Once saved, the following fields are **immutable** — they cannot be changed, overwritten, or nullified:

- `receipt_number`
- `payment_id`
- `invoice_id`
- `client_id`
- `created_at`

All snapshot fields (§3) are also immutable after save. A receipt is a frozen record; it does not update.

### 1.3 Relationship to Payment

One payment produces exactly one receipt. The receipt is generated automatically when `recordPayment()` succeeds. The receipt's `payment_id` is the canonical link back to the payment record.

If a payment is voided (via `payments.voided_at`), the receipt remains but its status transitions to `voided`. The receipt is never deleted.

## 2. Receipt Snapshot Law

**Every field on a receipt is a snapshot taken at payment recording time.** A receipt never joins live tables, never reads from `settings`, never fetches from `clients`, and never queries `projects` at render time.

This is the Receipt module's core invariant. It satisfies `docs/PRD/financial-operations-prd.md` §7.4.6: "Payment receipt data is immutable and independent of invoice state changes."

### 2.1 What Must Be Frozen

| Category | Fields | Source at Payment Time |
|----------|--------|----------------------|
| **Payment** | `amount`, `date`, `method`, `reference`, `cash_amount`, `wht_amount`, `currency_code`, `wht_rate`, `wht_type` | `payments` table row (already frozen) |
| **Invoice** | `invoice_number`, `total`, `subtotal`, `vat`, `wht`, `discount`, `status`, `notes`, `terms`, `po_number` | `invoices` table via JOIN |
| **Client** | `client_name`, `client_address`, `client_city`, `client_state`, `client_phone`, `client_email` | `clients` table via `invoices.client_id` |
| **Project** | `project_name`, `project_code` | `projects` table via `invoices.project_id` |
| **Company** | `company_name`, `company_address`, `company_email`, `company_phone`, `company_logo_url` | `settings` table (singleton) |
| **Bank** | `bank_name`, `bank_account_number`, `bank_account_name` | `bank_accounts` table via `payments.bank_account_id` |
| **Signatory** | `signatory_name`, `signatory_role`, `signatory_signature_url` | `signatories` table |

### 2.2 What Must NOT Be Frozen

- `invoice_financials_v` — this is a live recomputed view; never reference it for receipts
- Computed balance due — store the invoice total and payment amount separately; derive balance on display if needed
- Any future/computed field that depends on other payments

### 2.3 Snapshot Builder Pattern

The receipt snapshot is built inside `recordPayment()` after the payment INSERT succeeds. The builder:

1. Fetches invoice, client, project, company, bank, and signatory data via JOINs
2. Denormalizes all fields onto the receipt row
3. Inserts the receipt row in the same transaction as the payment (or immediately after, with compensation on failure)

```ts
// pseudocode — NOT the actual implementation
async function buildReceiptSnapshot(paymentId: string, invoiceId: string): Promise<ReceiptSnapshot> {
  const invoice = await fetchInvoiceWithClient(invoiceId)  // includes client fields
  const company = await fetchCompanySettings()              // singleton
  const bank = await fetchBankAccount(invoice.payment.bank_account_id)
  const signatory = await fetchDefaultSignatory()

  return {
    // payment fields (already on payment row)
    payment_amount: payment.amount,
    payment_date: payment.date,
    payment_method: payment.method,
    payment_reference: payment.reference,
    // ... other payment fields

    // invoice snapshot
    invoice_number: invoice.invoice_number,
    invoice_total: invoice.total,
    invoice_subtotal: invoice.subtotal,
    invoice_vat: invoice.vat,
    invoice_wht: invoice.wht,
    invoice_discount: invoice.discount,
    invoice_notes: invoice.notes,
    invoice_terms: invoice.terms,
    invoice_po_number: invoice.po_number,

    // client snapshot
    client_name: invoice.client.name,
    client_address: invoice.client.address,
    client_city: invoice.client.city,
    client_state: invoice.client.state,
    client_phone: invoice.client.phone,
    client_email: invoice.client.email,

    // project snapshot
    project_name: invoice.project?.name ?? null,
    project_code: invoice.project?.project_code ?? null,

    // company snapshot
    company_name: company.company_name,
    company_address: company.company_address,
    company_email: company.company_email,
    company_phone: company.company_phone,
    company_logo_url: company.company_logo_url,

    // bank snapshot
    bank_name: bank.bank_name,
    bank_account_number: bank.account_number,
    bank_account_name: bank.account_name,

    // signatory snapshot
    signatory_name: signatory.name,
    signatory_role: signatory.role,
    signatory_signature_url: signatory.signature_url,
  }
}
```

## 3. Storage Contract

### 3.1 Database Table: `receipts`

```sql
CREATE TABLE receipts (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  receipt_number TEXT UNIQUE NOT NULL,

  -- FK links (immutable after save)
  payment_id UUID NOT NULL REFERENCES payments(id),
  invoice_id UUID NOT NULL REFERENCES invoices(id),
  client_id UUID NOT NULL REFERENCES clients(id),

  -- Payment snapshot (already on payments, duplicated here for independence)
  payment_amount NUMERIC NOT NULL,
  payment_date DATE NOT NULL,
  payment_method TEXT,
  payment_reference TEXT,
  payment_notes TEXT,
  cash_amount NUMERIC DEFAULT 0,
  wht_amount NUMERIC DEFAULT 0,
  currency_code TEXT DEFAULT 'NGN',
  wht_rate NUMERIC,
  wht_type TEXT,

  -- Invoice snapshot
  invoice_number TEXT NOT NULL,
  invoice_total NUMERIC,
  invoice_subtotal NUMERIC,
  invoice_vat NUMERIC,
  invoice_wht NUMERIC,
  invoice_discount NUMERIC,
  invoice_notes TEXT,
  invoice_terms TEXT,
  invoice_po_number TEXT,

  -- Client snapshot
  client_name TEXT NOT NULL,
  client_address TEXT,
  client_city TEXT,
  client_state TEXT,
  client_phone TEXT,
  client_email TEXT,

  -- Project snapshot
  project_name TEXT,
  project_code TEXT,

  -- Company snapshot
  company_name TEXT NOT NULL,
  company_address TEXT,
  company_email TEXT,
  company_phone TEXT,
  company_logo_url TEXT,

  -- Bank snapshot
  bank_name TEXT,
  bank_account_number TEXT,
  bank_account_name TEXT,

  -- Signatory snapshot
  signatory_name TEXT,
  signatory_role TEXT,
  signatory_signature_url TEXT,

  -- Lifecycle
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'voided')),
  voided_at TIMESTAMPTZ,
  void_reason TEXT,

  -- Audit
  created_by UUID REFERENCES auth.users(id),
  created_at TIMESTAMPTZ DEFAULT now() NOT NULL
);

CREATE INDEX idx_receipts_payment_id ON receipts(payment_id);
CREATE INDEX idx_receipts_invoice_id ON receipts(invoice_id);
CREATE INDEX idx_receipts_client_id ON receipts(client_id);
CREATE UNIQUE INDEX idx_receipts_number ON receipts(receipt_number);
```

### 3.2 Immutability Enforcement

After a receipt is inserted, **no UPDATE or DELETE is permitted** except for:

- `status` transition to `'voided'` (with `voided_at` and `void_reason`)
- `created_by` backfill (if not set at creation time)

The application layer MUST enforce this via:
1. Repository-level guard: `updateReceipt()` only allows `status`, `voided_at`, `void_reason` fields
2. Domain-level assertion: `assertReceiptImmutable()` throws if any snapshot field is modified

### 3.3 Voided Receipts

A receipt can be voided only when its linked payment is voided (`payments.voided_at` is set). The receipt's `status` transitions to `'voided'` but all snapshot fields remain intact. A voided receipt is still a legal record — it proves a payment was recorded and later reversed.

## 4. Prefix Engine Compliance

### 4.1 Registration

The receipt module requires a new key in the prefix engine:

```ts
// src/domain/prefixConstants.ts
export const DEFAULT_PREFIXES = {
  waybill: 'WBL',
  invoice: 'INV',
  boq: 'BOQ',
  rfq: 'RFQ',
  quotation: 'QTN',
  project: 'PRJ',
  csr: 'CSR',
  receipt: 'RCP',   // NEW
} as const

export type DocumentPrefixKey = keyof typeof DEFAULT_PREFIXES
```

### 4.2 DB CHECK Constraint

A new migration must update the `settings.document_prefixes` CHECK constraint to include `receipt`:

```sql
ALTER TABLE settings DROP CONSTRAINT settings_document_prefixes_check;
ALTER TABLE settings ADD CONSTRAINT settings_document_prefixes_check
  CHECK (document_prefixes <@ jsonb_build_object(
    'waybill', ..., 'invoice', ..., 'boq', ..., 'rfq', ...,
    'quotation', ..., 'project', ..., 'csr', ..., 'receipt', ...
  ));
```

### 4.3 Number Format

Receipts follow the standard format from `docs/STANDARD/prefix-engine-settings-standard.md` §1.4:

```
{resolvedPrefix}-{6-digit serial}
```

Examples: `RCP-000001`, `RCP-000002`, `RCP-000123`.

No routing token is needed for receipts (unlike waybills).

### 4.4 Number Generation

```ts
// src/domain/receipt/receiptNumber.ts
import { resolvePrefix, type DocumentPrefixes } from '../prefixConstants'

export function getNextReceiptNumber(
  rows: { receipt_number?: string | null }[],
  prefix: string = 'RCP',
): string {
  const maxSerial = rows.reduce((max, row) => {
    const match = row.receipt_number?.match(/-(\d{6})$/)
    if (match) {
      const serial = parseInt(match[1], 10)
      return serial > max ? serial : max
    }
    return max
  }, 0)

  return `${prefix}-${String(maxSerial + 1).padStart(6, '0')}`
}
```

### 4.5 Insert Wrapper

Receipt INSERT must use `withUniqueRetry` per `docs/STANDARD/prefix-engine-settings-standard.md` §2:

```ts
const { data, error } = await withUniqueRetry(
  async (candidateNumber: string) => {
    payload.receipt_number = candidateNumber
    return supabase.from('receipts').insert([payload]).select().single()
  },
  async () => {
    const { data: rows } = await supabase
      .from('receipts')
      .select('receipt_number')
    return getNextReceiptNumber(rows || [], resolvePrefix(prefixes, 'receipt'))
  },
)
```

## 5. Lifecycle

### 5.1 States

| State | Description |
|-------|-------------|
| `active` | Receipt is valid and represents a live payment record. Default state at creation. |
| `voided` | Receipt's linked payment was voided. Snapshot data remains intact. |

### 5.2 Transitions

```
active → voided   (when payment is voided)
```

No other transitions are permitted. There is no `draft` state — receipts are created atomically with payment recording and are immediately active.

### 5.3 Creation Trigger

A receipt is created **automatically** when `recordPayment()` succeeds. The receipt is NOT created separately or on-demand. The flow:

1. User records a payment via `recordPayment()`
2. Payment is inserted into `payments` table
3. `buildReceiptSnapshot()` is called with the payment and invoice data
4. Receipt is inserted into `receipts` table with `status = 'active'`
5. If receipt insert fails, payment is NOT rolled back (receipt generation is best-effort; can be retried via a background job or admin tool)

### 5.4 Voiding

When a payment is voided via `voidPayment()`:

1. `payments.voided_at` is set
2. The linked receipt's `status` transitions to `'voided'`
3. `receipts.voided_at` and `receipts.void_reason` are populated

### 5.5 No Edit / No Duplicate / No Revert

Receipts do not support:
- **Edit** — A receipt is a frozen record. If the underlying data was wrong, void the receipt and record a new payment.
- **Duplicate** — Receipts are generated, not created by users. Duplication would create a second proof-of-payment for the same payment.
- **Revert** — Receipts are not part of the document transformation chain (quotation → invoice → waybill). They are downstream artifacts.

This aligns with the Receipt's role as a **proof-of-payment**, not a **request-for-payment**.

## 6. Rendering Rules

### 6.1 PDF Generation

Receipt PDFs are generated via the existing PDF pipeline (`@react-pdf/renderer`). The receipt PDF template receives pre-shaped data from a preview model — it does not compute, join, or fetch.

### 6.2 Required PDF Sections

| Section | Content |
|---------|---------|
| **Header** | Company logo, company name, address, email, phone |
| **Title** | "PAYMENT RECEIPT" |
| **Receipt Number** | `receipt_number` (e.g. RCP-000001) |
| **Date** | `payment_date` |
| **Client Block** | Client name, address, city, state, phone, email |
| **Payment Details** | Amount, method, reference, cash amount, WHT amount |
| **Invoice Reference** | Invoice number, total, subtotal, VAT, WHT, discount |
| **Project Reference** | Project name and code (if present) |
| **Bank Details** | Bank name, account number, account name |
| **Signatory** | Name, role, signature image |
| **Footer** | "This is a computer-generated receipt. No signature required." |

### 6.3 Design Constraints

- No framer-motion components (per AGENTS.md §2)
- Follow existing PDF template patterns in `src/components/pdf-new/`
- Receipt template must be a dumb renderer — receives data, outputs PDF. No business logic.

## 7. Transformation Compliance

### 7.1 Receipt Is Not Part of the 3 Laws System

The Document Transformation Standard (`docs/STANDARD/document-transformation-standard.md`) governs Invoice, Quotation, Waybill, CSR, BOQ, RFQ. **Receipt is not in this list.**

Receipts do not:
- Convert to/from other document types
- Duplicate (they are system-generated, not user-created)
- Revert (they are not part of the quotation → invoice chain)

### 7.2 Receipt Is Downstream of Payments

The receipt inherits its identity from the payment. The payment's `voided_at` controls the receipt's `status`. The receipt does not have its own independent lifecycle — it is a **projection** of the payment record.

### 7.3 Domain Segregation

Per AGENTS.md §2 — "PDFs are dumb renderers that receive shaped data via preview functions; they never compute prices, taxes, or totals."

The receipt PDF template receives `ReceiptPreviewData` (§6.4) and renders it. It does not:
- Query the database
- Compute totals
- Join tables
- Read from `settings`

### 7.4 Monetary Value Handling

Unlike waybill transformation (where monetary values are stripped), receipt transformation **preserves** all monetary values. The receipt is a financial record — it must show the exact amounts paid.

|-------|------|-------------|

## 9. Future Extension Points

This section documents known future needs. These are NOT implemented in v1.0 and MUST NOT be built until explicitly requested.

### 9.1 Receipt Email Delivery

Send receipt PDF to client via email. Requires:
- Email service integration
- Client email address validation
- Delivery status tracking

### 9.2 Receipt List View

A page to browse, search, and filter receipts. Requires:
- `src/pages/Receipts.tsx` (list page)
- `src/pages/ReceiptDetail.tsx` (detail view)
- Search by receipt number, client name, invoice number, date range

### 9.3 Bulk Receipt Generation

Generate receipts for multiple payments at once. Requires:
- Batch processing pipeline
- Progress indication
- Error handling per-receipt

### 9.4 Receipt Regeneration

Regenerate a receipt's PDF without changing the snapshot data. This is a read-only operation — the receipt row is not modified.

### 9.5 Receipt Attachments

Attach supporting documents (e.g., bank transfer slips) to a receipt. Requires:
- `receipt_attachments` table
- File upload pipeline
- Storage bucket configuration

### 9.6 Receipt Number Override

Allow manual receipt number entry for backward compatibility with pre-existing receipts. This would require:
- UI toggle for manual entry
- Validation against uniqueness
- Bypass of prefix engine when manual
