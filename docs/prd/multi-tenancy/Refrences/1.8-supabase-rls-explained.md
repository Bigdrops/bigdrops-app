## Why This Reference Exists

This article addresses a specific edge case in Supabase multi-tenant RLS: when policies need to reference data in other schemas. This is relevant to BIGDROPS because the `entities` table (public schema) may need to be referenced in RLS policies for entity-scoped tables (schema-per-entity or row-level entity filtering).

## Relevant Architecture / Patterns

- **Cross-schema RLS** — policies that reference tables in other schemas (e.g., checking membership in `public.workspace_members` from a policy on `entity_xxx.invoices`).
- **Schema-per-tenant vs row-level tenant isolation** — tradeoffs between the two approaches.
- **RLS policy complexity** — as policies reference more tables, they become harder to reason about and test.
- **Performance implications** — cross-schema references in RLS policies can cause sequential scans if not indexed properly.

## What BIGDROPS Should Borrow

- The warning about RLS policy complexity — BIGDROPS's two-level (workspace + entity) policies will be more complex than single-level; this article highlights the risks.
- The cross-schema reference pattern — if BIGDROPS ever uses entity-specific schemas, this pattern applies.
- The performance warning — RLS policies with subqueries can be slow; index the columns used in policy predicates.

## What BIGDROPS Must NOT Adopt

- Schema-per-tenant as the default approach — BIGDROPS uses shared-schema (pool model) per §5-§6.
- Overly complex cross-schema policies — BIGDROPS should keep policies as simple as possible, referencing only the necessary tables.
- Any patterns that weaken isolation for performance — security first.

## Known Limitations

## Bottom Line

Useful as a warning about RLS policy complexity and cross-schema references. BIGDROPS should keep its RLS policies simple and avoid cross-schema references unless absolutely necessary.
