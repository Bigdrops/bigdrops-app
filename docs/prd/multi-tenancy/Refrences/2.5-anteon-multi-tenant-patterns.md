## Why This Reference Exists

Anteon catalogues 9 multi-tenant patterns with explicit pros and cons. This provides a decision framework for BIGDROPS to validate its architectural choices against the full spectrum of available patterns.

## Relevant Architecture / Patterns

- **9 patterns** including:
  - **Shared database, shared schema** (pool) — BIGDROPS's current choice.
  - **Shared database, separate schemas** (bridge) — potential future option.
  - **Separate database per tenant** (silo) — enterprise option.
  - **Row-level security** — BIGDROPS's §6 approach.
  - **Application-level isolation** — filtering in app code (not recommended for BIGDROPS).
  - **Hybrid approaches** — mixing patterns for different data sensitivity levels.
- **Pros and cons for each pattern** — explicit tradeoffs.
- **Decision criteria** — tenant count, data sensitivity, cost, complexity.

## What BIGDROPS Should Borrow

- The **decision framework** — validates that pool + RLS is correct for BIGDROPS's current scale and needs.
- The warning against **application-level-only isolation** — BIGDROPS must use database-level RLS.
- The concept of **hybrid approaches** — some tables may eventually need different isolation (e.g., financial data in a separate schema).
- The **tenant count guidance** — pool works for most SaaS up to hundreds of tenants.

## What BIGDROPS Must NOT Adopt

- Silo patterns as the default — BIGDROPS is pool-model per §5-§6.
- Application-level filtering as a substitute for RLS — always use database-level policies.
- Over-engineering for scale BIGDROPS has not reached.

## Known Limitations

## Bottom Line

Useful decision framework for validating BIGDROPS's architectural choices. The pool + RLS pattern is confirmed as the right choice for BIGDROPS's current scale. The hybrid approach concept is worth noting for future scaling.
