## Why This Reference Exists

arc42 provides architecture-level guidance on multi-tenancy approaches, including when to use pool vs silo vs bridge models. This helps BIGDROPS validate its §5-§6 architectural choices against established patterns.

## Relevant Architecture / Patterns

- **Pool vs Silo vs Bridge** — three tenant isolation models with tradeoffs:
  - **Pool**: Shared database, shared schema, `tenant_id` column. Lowest cost, most complex RLS.
  - **Silo**: Separate database or schema per tenant. Highest isolation, highest cost.
  - **Bridge**: Hybrid — shared database, separate schemas per tenant.
- **BIGDROPS is pool-model** — shared schema, `workspace_id` + `entity_id` columns.
- **Tenant isolation as a spectrum** — not binary; different tables may need different isolation levels.
- **Cost vs isolation tradeoff** — pool is cheapest, silo is most isolated.

## What BIGDROPS Should Borrow

- The **pool vs silo vs bridge** framework for reasoning about isolation choices.
- The validation that pool-model (shared schema + RLS) is the correct choice for BIGDROPS's current scale.
- The concept of **tenant isolation as a spectrum** — some tables may eventually need schema-level isolation (e.g., for enterprise customers).

## What BIGDROPS Must NOT Adopt

- Silo or bridge patterns as the default — BIGDROPS is pool-model per §5-§6.
- Over-engineering isolation for current needs — pool + RLS is sufficient for BIGDROPS's scale.
- Generic multi-tenancy advice that doesn't account for BIGDROPS's two-level (workspace + entity) model.

## Known Limitations

- Architecture-level guidance; not implementation-specific.
- No entity lifecycle (§8A) coverage.
- Does not address Supabase-specific patterns.

## Bottom Line

Good architectural framework for reasoning about tenant isolation. Validates BIGDROPS's pool-model choice. The pool/silo/bridge taxonomy is useful for future architectural decisions if BIGDROPS scales to enterprise tenants.
