## Why This Reference Exists

AWS provides the most detailed publicly available documentation on fine-grained authorization for multi-tenant SaaS. The PDP/PEP (Policy Decision Point / Policy Enforcement Point) separation, RBAC vs ABAC taxonomy, and the distinction between tenant isolation and authorization are directly relevant to BIGDROPS §3.

## Relevant Architecture / Patterns

- **PDP/PEP separation** — Policy Decision Point evaluates permissions; Policy Enforcement Point enforces them. BIGDROPS edge functions act as PEP; RLS acts as PDP for row-level access.
- **RBAC vs ABAC** — Role-Based (roles map to permissions) vs Attribute-Based (attributes map to permissions). BIGDROPS §3 is RBAC with editable permission bundles.
- **Tenant isolation ≠ authorization** — isolation (can I see this tenant?) is a different layer from authorization (can I do this action?). Both are needed.
- **Action-based permit policies** — policies that permit specific actions on resources, not just CRUD operations. BIGDROPS §3 uses action-based abilities.
- **Per-tenant policy stores** — each tenant has its own policy set. BIGDROPS does not need this at current scale.

## What BIGDROPS Should Borrow

- The **PDP/PEP mental model** — BIGDROPS edge functions (PEP) evaluate permissions (PDP) before executing actions.
- The **isolation ≠ authorization** principle — BIGDROPS §6 (RLS) handles isolation; §3 (permissions) handles authorization. These are complementary.
- The **action-based permit** pattern — BIGDROPS §3 abilities like `invoice:create` match this model.
- The warning that **tenant context must be resolved before action authorization** — same as Agnite's four-step sequence.

## What BIGDROPS Must NOT Adopt

- Amazon Verified Permissions as a dependency — BIGDROPS uses its own permission model.
- Per-tenant policy stores — over-engineered for BIGDROPS's current needs.
- ABAC patterns — BIGDROPS uses RBAC with editable bundles, not attribute-based policies.
- AWS-specific infrastructure patterns (IAM, Cedar policies).

## Known Limitations

- AWS-centric; assumes AWS infrastructure.
- Over-engineered for BIGDROPS's current scale.
- No entity lifecycle (§8A) coverage.
- The Cedar policy language is specific to AWS Verified Permissions.

## Bottom Line

The PDP/PEP separation and isolation ≠ authorization principle are the most valuable concepts. BIGDROPS should adopt the mental model without the AWS-specific implementation. The action-based permit pattern validates BIGDROPS's §3 design.
