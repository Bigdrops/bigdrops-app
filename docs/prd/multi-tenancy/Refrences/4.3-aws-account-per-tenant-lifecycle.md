## Why This Reference Exists

AWS documents the account lifecycle state machine for account-per-tenant SaaS: `ACTIVE → SUSPENDED → CLOSED`. While BIGDROPS uses pool-model (not account-per-tenant), the lifecycle state machine concept directly informs §8A (entity lifecycle).

## Relevant Architecture / Patterns

- **Lifecycle state machine** — `ACTIVE → SUSPENDED → CLOSED` with explicit transitions.
- **Suspended vs workload states** — suspended accounts retain data but cannot be accessed; workload is the operational state.
- **Deprovision then delete** — never delete immediately; deprovision (suspend) first, then delete after retention.
- **Do not reuse suspended accounts** — once suspended, the account identifier is retired.
- **Audit trail** — every lifecycle transition is logged.

## What BIGDROPS Should Borrow

- The **state machine** concept — BIGDROPS §8A uses `active → archived → purging → purged`, which is the same pattern.
- The **deprovision then delete** principle — archive before purge; BIGDROPS §8A enforces this.
- The **do not reuse** principle — once an entity is purged, its identifier is retired.
- The **audit trail** requirement — BIGDROPS `entity_lifecycle_audit` follows this.

## What BIGDROPS Must NOT Adopt

- Account-per-tenant model — BIGDROPS uses pool-model (shared schema) per §5-§6.
- AWS-specific infrastructure patterns (Organizations, Control Tower).
- The `SUSPENDED` state — BIGDROPS uses `archived` instead, with a 30-day retention gate before purge.

## Known Limitations

- AWS-centric; assumes account-per-tenant model.
- No discussion of pool-model lifecycle.
- No entity lifecycle (§8A) coverage at the database level.

## Bottom Line

The lifecycle state machine concept is directly applicable. The deprovision-then-delete and do-not-reuse principles are validated. BIGDROPS §8A's state machine (`active → archived → purging → purged`) is the correct adaptation of this pattern for pool-model tenancy.
