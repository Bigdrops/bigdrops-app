## Why This Reference Exists

AWS published this as a canonical reference for shared-schema multi-tenant RLS on Supabase. It covers the exact pattern BIGDROPS uses: shared Postgres database, `tenant_id` column, RLS policies, and session-variable tenant context. The production-oriented isolation notes go beyond tutorial-level material.

## Relevant Architecture / Patterns

- **Shared-schema + `tenant_id` + session variable** — the core pattern: `SET app.current_tenant` → RLS policies filter on `current_setting('app.current_tenant')`.
- **`FORCE ROW LEVEL SECURITY`** on all tenant tables — prevents table-owner bypass.
- **Owner-bypass pitfalls** — documents when and why `BYPASSRLS` or table-owner access breaks isolation.
- **Index strategy** — composite indexes with `tenant_id` as leading column for policy predicate performance.
- **Policy shape** — separate SELECT/INSERT/UPDATE/DELETE policies with USING and WITH CHECK.

## What BIGDROPS Should Borrow

- The session-variable pattern (`SET app.current_tenant`) as an alternative to `auth.jwt()` for server-side contexts where JWT is not available (cron jobs, database triggers, admin operations).
- The `FORCE ROW LEVEL SECURITY` requirement — this is the same conclusion BIGDROPS §6 reaches.
- The owner-bypass documentation — critical for understanding when Supabase service role or migration runner can accidentally bypass RLS.
- The index strategy — composite indexes with tenant key as leading column.

## What BIGDROPS Must NOT Adopt

- The single-level `tenant_id` model. BIGDROPS has workspace + entity (two levels); the sample only addresses single-level isolation.
- The AWS-centric deployment assumptions — BIGDROPS runs on Vercel + Supabase, not AWS infrastructure.
- Any migration patterns that assume direct Postgres access without Supabase's migration tooling.

## Known Limitations

- Single-level tenancy only — does not address the workspace-entity hierarchy.
- No entity lifecycle (§8A) coverage — archive/purge state transitions are not discussed.
- Sample application complexity may be over-engineered for BIGDROPS's current needs.

## Bottom Line

A production-quality reference for RLS on Supabase. The session-variable pattern, FORCE RLS, and index strategy are directly applicable. BIGDROPS must extend the single-level model to handle workspace+entity.
