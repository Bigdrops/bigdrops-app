## Why This Reference Exists

Nile is a Postgres platform designed specifically for multi-tenant SaaS. Their blog covers the exact request lifecycle for RLS: authenticate → set context → query → RLS filters rows. This matches BIGDROPS's architecture and provides clear mental models for §6.

## Relevant Architecture / Patterns

- **Request lifecycle**: Request arrives → authenticate user → set tenant context (`SET LOCAL tenant_id`) → execute query → RLS filters rows → return results.
- **Fails-closed by default**: If tenant context is not set, RLS policies deny access. This is the safe default.
- **Policies on tables > filters on every query**: RLS is enforced once at the database level, not scattered across application code.
- **`auth.uid()` for user context** — same pattern BIGDROPS uses via Supabase Auth.
- **Composite policies** — combine user membership AND tenant context in a single policy for authorization + isolation.

## What BIGDROPS Should Borrow

- The **fails-closed** mental model: if tenant context is missing, deny access. BIGDROPS §6 should follow this principle.
- The argument for **database-level policies over application-level filters** — this validates BIGDROPS's RLS-first approach.
- The composite policy pattern: `USING (workspace_id = ? AND auth.uid() IN (SELECT user_id FROM workspace_members WHERE workspace_id = ?))`.
- The request lifecycle model — useful for documenting how BIGDROPS edge functions should set tenant context.

## What BIGDROPS Must NOT Adopt

- Nile's platform-specific features (their tenant-management API, virtual tenant databases). BIGDROPS uses standard Supabase.
- The single-level tenant model — Nile's blog shows single `tenant_id`; BIGDROPS has workspace + entity.
- Any assumption that the database handles tenant switching automatically — BIGDROPS manages this in the application layer.

## Known Limitations

- Nile has a commercial interest in promoting their multi-tenant platform; their blog is educational but also marketing.
- Single-level tenancy only — does not address workspace-entity hierarchy.
- No entity lifecycle (§8A) coverage.

## Bottom Line

Excellent conceptual reference for understanding RLS in multi-tenant Postgres. The fails-closed model, composite policies, and request lifecycle are directly applicable to BIGDROPS §6. Must be adapted for two-level tenancy.
