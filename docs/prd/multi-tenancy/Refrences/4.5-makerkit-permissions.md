## Why This Reference Exists

Makerkit defines the capability-style permission model for multi-tenant SaaS: permission keys like `billing:update` rather than CRUD verbs. This directly maps to BIGDROPS §3's action-based abilities.

## Relevant Architecture / Patterns

- **Capability-style permissions** — permission keys like `billing:update`, `invoice:create`, `settings:manage`. BIGDROPS §3 uses action-based abilities.
- **Roles as permission sets** — roles group capabilities into reusable sets. BIGDROPS §3.11 defines editable role bundles.
- **Working `accounts` + membership + RLS** — a complete implementation of workspace + membership + RLS on Supabase/Next.js.
- **Permission evaluation** — check user's role → check role's permissions → check resource access.

## What BIGDROPS Should Borrow

- The **capability-style permission keys** — BIGDROPS §3 abilities like `invoice:create` match this pattern.
- The **roles as permission sets** — validates BIGDROPS §3.11's editable role bundles.
- The **accounts + membership + RLS** implementation — a working reference for Supabase multi-tenancy.

## What BIGDROPS Must NOT Adopt

- Makerkit as a dependency — BIGDROPS has its own domain logic.
- Next.js-specific patterns — BIGDROPS uses Vite + React.
- The specific permission key naming convention — BIGDROPS has its own ability taxonomy (§3).
- Any patterns that assume a different auth provider.

## Known Limitations

- Makerkit-specific; patterns are tied to Makerkit's framework.
- No entity lifecycle (§8A) coverage.
- Does not address two-level tenancy (workspace + entity).

## Bottom Line

The capability-style permission pattern is directly applicable. The roles-as-permission-sets concept validates BIGDROPS §3.11. Use as a conceptual reference; do not copy implementation.
