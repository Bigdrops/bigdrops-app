## Why This Reference Exists

Clerk defines the industry-standard B2B multi-tenant model: shared user pool, organization (workspace) membership, roles per organization, personal vs org resources. BIGDROPS §5 (workspace model) and §7-§9 (invites, membership) map directly to this pattern.

## Relevant Architecture / Patterns

- **Organization ≈ Workspace** — Clerk's `Organization` maps to BIGDROPS's `workspaces` table.
- **Membership join table** — users belong to organizations through a many-to-many membership, not by owning a `tenant_id` column.
- **Roles per organization** — a user can be `admin` in Org A and `member` in Org B. Roles are scoped to the org, not global.
- **Personal vs org resources** — some data belongs to the user (profile), some belongs to the org (invoices, team data).
- **Organization switcher** — UI pattern for switching between organizations.
- **Invitation lifecycle** — invite → accept → create membership; tokens with expiry; pending vs accepted states.

## What BIGDROPS Should Borrow

- The **membership join table** pattern — BIGDROPS `workspace_members` follows this.
- The **roles per organization** pattern — BIGDROPS §3 permissions are scoped to workspace.
- The **invitation lifecycle** — BIGDROPS §9 invites should follow Clerk's成熟 model: token, expiry, accept with/without existing account.
- The **organization switcher** UI pattern — BIGDROPS's entity switcher is the same concept at a second level.
- The **personal vs org resources** distinction — useful for BIGDROPS's user settings (personal) vs workspace data (shared).

## What BIGDROPS Must NOT Adopt

- Clerk as a dependency — BIGDROPS uses Supabase Auth, not Clerk.
- Clerk's specific API surface — BIGDROPS has its own domain functions.
- The single-level org model — BIGDROPS has workspace + entity (two levels); Clerk only shows org + member.
- Clerk's billing integration patterns — BIGDROPS handles billing differently.

## Known Limitations

- Clerk-specific; some patterns are tied to Clerk's hosted UI and API.
- Single-level organization — does not address workspace-entity hierarchy.
- No entity lifecycle (§8A) coverage.
- Clerk's role model is simpler than BIGDROPS's action-permission model (§3).

## Bottom Line

The industry-standard reference for B2B multi-tenant workspace + membership + roles. The membership join table, invitation lifecycle, and org switcher patterns are directly applicable. BIGDROPS must extend this for two-level tenancy.
