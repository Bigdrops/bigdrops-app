## Why This Reference Exists

This repository provides a ready-made multi-tenant RBAC extension for Supabase: groups, members, roles, and permission helpers for RLS. It directly addresses BIGDROPS's needs for §3 (permissions) + §6 (RLS) integration.

## Relevant Architecture / Patterns

- **Groups** (≈ workspaces) — the tenant entity; permissions are scoped to groups.
- **Members** — many-to-many between users and groups.
- **Roles** — role definitions scoped to groups; roles map to permissions.
- **Permission helpers for RLS** — utility functions that simplify RLS policy writing (e.g., `is_member_of(group_id)`, `has_permission(permission_key)`).
- **RLS integration** — permissions are evaluated at the database level, not just in application code.

## What BIGDROPS Should Borrow

- The **permission helpers for RLS** — utility functions that simplify policy writing. BIGDROPS could create similar helpers for workspace + entity RLS.
- The **groups + members + roles** pattern — validates BIGDROPS's membership model.
- The **RLS integration** — permissions evaluated at the database level, not just in app code.
- The concept of **scoping permissions to groups** — BIGDROPS scopes permissions to workspaces.

## What BIGDROPS Must NOT Adopt

- The specific extension as a dependency — BIGDROPS has its own permission model (§3).
- Single-level group model — BIGDROPS has workspace + entity (two levels).
- Any patterns that assume a different Supabase setup.

## Known Limitations

- Single-level group model — does not address workspace-entity hierarchy.
- No entity lifecycle (§8A) coverage.
- License may restrict usage in proprietary projects.
- May not address all of BIGDROPS's permission edge cases.

## Bottom Line

The permission helpers for RLS pattern is the most valuable concept — utility functions that simplify policy writing. BIGDROPS should create similar helpers for its two-level model. The groups + members + roles pattern validates the membership model.
