## Why This Reference Exists

Prisma's guide covers multi-tenant RBAC with a permission model: roles → permissions → resources. While BIGDROPS uses Supabase (not Prisma), the permission model concepts are relevant to §3 (permissions).

## Relevant Architecture / Patterns

- **Roles → Permissions → Resources** — hierarchical permission model.
- **Tenant-scoped roles** — roles are scoped to a tenant (workspace), not global.
- **Permission evaluation** — check role → check permissions → check resource access.
- **Prisma RLS client extension** — Prisma's approach to setting tenant context (similar to `SET LOCAL` in raw Postgres).

## What BIGDROPS Should Borrow

- The **role → permission → resource** hierarchy — BIGDROPS §3 maps roles to action permissions.
- The **tenant-scoped roles** concept — BIGDROPS roles are workspace-scoped per §3.
- The Prisma RLS extension approach — conceptually similar to BIGDROPS's `SET LOCAL` for tenant context, though BIGDROPS uses Supabase client instead of Prisma.

## What BIGDROPS Must NOT Adopt

- Prisma as a dependency — BIGDROPS uses Supabase client, not Prisma.
- Prisma-specific patterns (client extensions, query middleware) — not applicable to BIGDROPS's stack.
- The specific permission model — BIGDROPS has its own action-permission model (§3).
- Prisma Postgres as a database — BIGDROPS uses standard Supabase Postgres.

## Known Limitations

- Prisma-specific; patterns are tied to Prisma's client library.
- No entity lifecycle (§8A) coverage.
- The permission model is simpler than BIGDROPS's action-permission model.

## Bottom Line

Conceptual reference for tenant-scoped RBAC. The role → permission → resource hierarchy is a useful mental model. Not directly applicable to BIGDROPS's stack (Supabase, not Prisma), but the patterns are transferable.
