## Why This Reference Exists

SSOJet covers pool vs silo identity models and many-to-many membership patterns. This is relevant to BIGDROPS's identity architecture — how users authenticate and how membership is modeled.

## Relevant Architecture / Patterns

- **Pool vs silo identity** — shared user pool (all tenants share one user table) vs separate user pools per tenant. BIGDROPS uses shared pool (Supabase Auth).
- **Many-to-many membership from day one** — users belong to multiple tenants through a membership join table. BIGDROPS `workspace_members` follows this.
- **Invitation flows** — invite → accept → create membership; token-based.
- **Role per tenant** — roles are scoped to the tenant, not global. BIGDROPS §3 maps to this.

## What BIGDROPS Should Borrow

- The **shared user pool** pattern — BIGDROPS uses Supabase Auth (shared pool) with workspace membership.
- The **many-to-many membership** from day one — validates BIGDROPS's membership model.
- The **invitation flow** — token, expiry, accept pattern.

## What BIGDROPS Must NOT Adopt

- SSOJet as a dependency — BIGDROPS uses Supabase Auth.
- SSO-specific patterns (SAML, OIDC) — not relevant for BIGDROPS's current auth model.
- Any patterns that assume a different auth provider.

## Known Limitations

- SSOJet-specific; some patterns are tied to SSOJet's product.
- No entity lifecycle (§8A) coverage.
- Does not address two-level tenancy (workspace + entity).

## Bottom Line

Conceptual reference for shared user pool + many-to-many membership. The patterns are applicable; the implementation is not (SSOJet-specific). Use as validation of BIGDROPS's identity architecture.
