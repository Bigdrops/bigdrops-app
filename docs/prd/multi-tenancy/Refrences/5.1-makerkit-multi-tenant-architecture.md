## Why This Reference Exists

Makerkit provides a complete working implementation of multi-tenant SaaS on Supabase: `accounts` table, membership join, RLS policies, permission evaluation. This is the most complete Supabase-specific reference for BIGDROPS's architecture.

## Relevant Architecture / Patterns

- **`accounts` table** (≈ workspaces) — the tenant entity.
- **Membership join table** — many-to-many between users and accounts.
- **RLS policies** — row-level security on all tenant-scoped tables.
- **Permission evaluation** — role-based with capability-style keys.
- **Supabase Auth integration** — uses Supabase Auth for user management.
- **Next.js frontend** — React-based, similar to BIGDROPS's stack.

## What BIGDROPS Should Borrow

- The **accounts + membership + RLS** pattern — directly applicable to BIGDROPS's workspace model.
- The RLS policy approach — policies that check membership, not just `tenant_id`.
- The Supabase Auth integration — wiring auth with workspace-level RLS.

## What BIGDROPS Must NOT Adopt

- Next.js-specific patterns — BIGDROPS uses Vite + React.
- The single-level account model — BIGDROPS has workspace + entity (two levels).
- Makerkit as a dependency — BIGDROPS has its own domain logic.
- Any patterns that assume service role on the client.

## Known Limitations

- Makerkit-specific; patterns are tied to Makerkit's framework.
- Single-level account — does not address entity hierarchy.
- No entity lifecycle (§8A) coverage.

## Bottom Line

The most complete Supabase-specific reference for multi-tenant SaaS. The accounts + membership + RLS pattern is directly applicable. Must be extended for two-level tenancy and entity lifecycle.
