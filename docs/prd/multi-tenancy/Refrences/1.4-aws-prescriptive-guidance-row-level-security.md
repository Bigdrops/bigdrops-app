## Why This Reference Exists

AWS Prescriptive Guidance provides the most detailed publicly available documentation on PostgreSQL RLS for multi-tenant SaaS. It covers policy shape, runtime context management, and enablement strategy — all directly relevant to BIGDROPS §6.

## Relevant Architecture / Patterns

- **Pool model** — shared database, shared schema, `tenant_id` column. This is the model BIGDROPS uses.
- **RLS policy structure**: `USING (tenant_id = current_setting('app.tenant_id')::uuid)` with `WITH CHECK` for writes.
- **`FORCE ROW LEVEL SECURITY`** — must be enabled on all tenant tables, including tables owned by the app role.
- **Runtime context**: `SET LOCAL app.tenant_id = '<uuid>'` at the start of each request transaction.
- **Policy evaluation**: PostgreSQL evaluates USING on SELECT, INSERT, UPDATE (old row), and DELETE; WITH CHECK on INSERT and UPDATE (new row).
- **Three tenant isolation models**: Pool (shared schema), Silo (separate schema/database), Bridge (hybrid). BIGDROPS is pool-model.
- **Authorization ≠ Isolation**: tenant isolation (RLS) is a different layer from action authorization (RBAC). Both are needed.

## What BIGDROPS Should Borrow

- The clear separation of **tenant isolation** (RLS, which row can I see?) from **action authorization** (RBAC, what can I do on that row?). BIGDROPS §3 (permissions) and §6 (RLS) map to these two layers.
- The `FORCE ROW LEVEL SECURITY` requirement — same conclusion as BIGDROPS §6.
- The `SET LOCAL` pattern for server-side tenant context.
- The policy-shape guidance: separate USING and WITH CHECK, index policy predicate columns.

## What BIGDROPS Must NOT Adopt

- The single-level tenant model — BIGDROPS has workspace + entity.
- AWS-specific infrastructure patterns (Aurora, RDS parameter groups) — BIGDROPS uses Supabase managed Postgres.
- The authorization patterns in the API authorization companion doc — they assume a PDP/PEP model that may be over-engineered for BIGDROPS's current needs.

## Known Limitations

- AWS-centric; some patterns assume direct control over database parameter groups and IAM.
- No entity lifecycle (§8A) coverage.
- The API authorization companion doc introduces Amazon Verified Permissions, which BIGDROPS does not use.

## Bottom Line

The most comprehensive publicly available guide on PostgreSQL RLS for multi-tenant SaaS. The isolation-vs-authorization separation, FORCE RLS, and policy-shape guidance are directly applicable. BIGDROPS must adapt the single-level model to its two-level hierarchy.
