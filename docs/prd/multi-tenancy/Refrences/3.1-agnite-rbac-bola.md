## Why This Reference Exists

Agnite defines the canonical request evaluation sequence for multi-tenant SaaS: Auth → Tenant Resolve → Isolation → Action Policy. This directly maps to BIGDROPS's request flow and §3 (permissions) + §6 (RLS) architecture.

## Relevant Architecture / Patterns

- **Request evaluation sequence**:
  1. **Auth** — who is this user? (`auth.uid()`)
  2. **Tenant Resolve** — which workspace/entity is this request for?
  3. **Isolation** — can this user access this tenant? (RLS / membership check)
  4. **Action Policy** — can this user perform this action on this resource? (RBAC / permissions)
- **BOLA (Broken Object Level Authorization)** — the #1 API vulnerability; occurs when isolation is not enforced.
- **Tenant-level BOLA** — cross-tenant data access; RLS prevents this.
- **Action-level BOLA** — unauthorized actions within a tenant; RBAC prevents this.
- **Two-layer security**: isolation (RLS) + authorization (RBAC) are complementary, not alternatives.

## What BIGDROPS Should Borrow

- The **four-step request evaluation sequence** — BIGDROPS should document this as its canonical request flow.
- The explicit separation of **isolation** (can I see this tenant?) from **authorization** (can I do this action?).
- The BOLA threat model — BIGDROPS's §6 RLS + §3 permissions address both tenant-level and action-level BOLA.
- The principle: **always evaluate tenant context first, then action permission**.

## What BIGDROPS Must NOT Adopt

- Any specific RBAC library or framework — BIGDROPS has its own permission model (§3).
- Over-engineering the authorization layer — BIGDROPS's action-permission model is simpler than full ABAC.
- Generic RBAC patterns that don't account for BIGDROPS's two-level (workspace + entity) model.

The four-step evaluation sequence (Auth → Tenant → Isolation → Action) is the clearest articulation of how BIGDROPS's request flow should work. The BOLA threat model validates the need for both RLS and RBAC. Directly applicable to BIGDROPS §3 + §6.
