# Invoice Identity Invariant Analysis

This report was written by Claude on 2026-07-03.

## Objective & Scope

This report determines whether runtime invocation of the existing `assertIdentityImmutable` invariant (`src/domain/invoice/assertIdentityImmutable.ts`) is necessary, or whether the Invoice architecture already guarantees identity immutability per the Document Transformation Standard's Edit Law.

**In scope:**
- Invoice save handler payload analysis
- `assertIdentityImmutable` field list vs. standard definition
- `SharedDocumentForm` / `ClientSelector` edit-mode behavior
- Lifecycle services (duplicate, revert, status change) identity mutation audit
- DB schema constraint analysis

**Out of scope:**
- Quotation, Waybill, CSR, RFQ, BOQ identity invariants
- Invoice architecture redesign
- Introduction of validation frameworks or lifecycle abstractions

Source: `docs/standard/document-transformation-standard.md`

- `document_number`

- `sourceDocumentType`
- `sourceDocumentNumber`

## Fact vs. Conclusion

### Facts (observed, verifiable)

1. `client_id` is included in every save payload and is mutable on edit
2. `client_name` is included in every save payload and is mutable on edit
3. `invoice_title` is included in every save payload and is mutable on edit
4. `document_type` is included in every save payload and is mutable on edit
5. The `ClientSelector` has no disabled/readonly mode — fully interactive in edit
6. `assertIdentityImmutable` is dead code — never called
7. `assertIdentityImmutable` checks `invoice_title`/`invoice_number`/`client_name`/`client_email`
8. The standard defines identity as `client_id`/`document_number`/`type`/lineage fields
9. `invoice_number` is create-only in the save payload — architecturally safe
10. The invoice table has no CHECK constraints preventing identity field changes
11. `type`, `sourceDocumentId`, `sourceDocumentType`, `sourceDocumentNumber` do not exist on the invoice table
12. No lifecycle service mutates identity fields outside expected operations

### Conclusions (interpretations)

**Conclusion 1: `client_id` is the primary identity vulnerability.**
The standard explicitly lists `client_id` as an identity field. The save handler sends it on every edit. The UI allows changing it. There is no runtime guard. A user can change the client on an existing invoice through normal UI interaction.

**Conclusion 2: `client_name` is a secondary vulnerability.**
Derives from `client_id` but is independently mutable. Changing `client_id` via `ClientSelector` also changes `client_name` via `handleClientChange`. The risk is lower since it's a derived field, but direct mutation is possible.

**Conclusion 3: `invoice_number` is architecturally safe.**
Create-only in the save payload. No service mutates it after creation. The `withUniqueRetry` utility prevents collisions at creation time. No invariant check needed.

**Conclusion 4: `invoice_title` and `document_type` are mutable but low-risk.**
These are presentation/business-logic fields, not core identity. The standard does not list them as identity fields. Mutability is expected behavior.

**Conclusion 5: Standard fields `type`, `sourceDocumentId`, `sourceDocumentType`, `sourceDocumentNumber` are not applicable.**
These fields do not exist on the invoice table. The invoice uses `linked_quote_id` for lineage and `document_type` instead of `type`. The standard's identity field list is a cross-document template; not all fields apply to every document type.

**Conclusion 6: The `assertIdentityImmutable` field list is wrong.**
It checks `invoice_title` and `client_email` (not identity per standard) and omits `client_id` (the actual identity field). Even if wired, it would not protect the right fields.

## Risk Assessment

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| Client changed on existing invoice via UI | Medium | Normal use — user can intentionally change client | No guard exists; behavior is currently unconstrained |
| Client name desynchronized from client ID | Low | Low — `ClientSelector` updates both atomically | `handleClientChange` sets both fields together |
| Invoice number mutated after creation | None | None — architecturally impossible | Create-only in save payload |
| `assertIdentityImmutable` wired with wrong fields | Medium | Would occur if function is wired without field reconciliation | Function must be reconciled with standard before wiring |

## Recommendation

**Wire `assertIdentityImmutable` at the save handler with corrected fields.**

The evidence shows that `client_id` is:
1. Explicitly an identity field per the Document Transformation Standard
2. Mutable on every edit through the normal UI flow
3. Not guarded by any runtime invariant
4. Not protected by DB constraints

The function should be updated to check:
- `client_id` (standard identity field, genuinely mutable)
- `invoice_number` (defense-in-depth, even though architecturally safe)

The function should NOT check:
- `invoice_title` (not identity per standard, expected to be editable)
- `client_email` (not on invoice table, not identity per standard)
- `type` / `sourceDocumentId` / `sourceDocumentType` / `sourceDocumentNumber` (do not exist on invoice table)

## Standalone Context

This report covers a forensic analysis of whether the Invoice module's `assertIdentityImmutable` function needs to be wired into the save handler. The investigation traced identity fields from the Document Transformation Standard through the save handler payload, form UI, lifecycle services, and DB schema. The core finding: `client_id` is an identity field that is mutable on edit with no guard. The existing function checks the wrong fields and must be reconciled before wiring. `invoice_number` is architecturally safe (create-only in payload). Standard fields `type`/lineage do not exist on the invoice table.
