## Key Decisions
- `resolveFinancialColumns` imported directly in callers rather than re-exported through `useInvoiceColumns`
- `ensureColumnOrderIntegrity` imported public `getResetColumnConfigs` from `columns.ts` instead of duplicating
- Private `getResetColumnConfigs` removed from resolver (was duplicating normalization logic — drift risk)
- EditInvoice stale-column fix: just removed the `if` guard, let `resolveFinancialColumns` handle null/undefined (returns BUILTIN_COLUMNS defaults) — works because `parsed && !Array.isArray(parsed)` is already checked before accessing `parsed.columnConfig`

## Critical Context
- `resolveFinancialColumns()` is deterministic: deduplicates by key (first occurrence wins), guarantees `description` at index 0, merges saved overrides atop builtin defaults, appends missing builtins at end
- `ensureColumnOrderIntegrity()` handles empty/invalid input by returning default column order
- `ColumnManager.tsx` renders builtin and custom columns in separate visual groups, but all index calculations use the full `columns` array — correct but visually confusing when columns are interleaved
- Three paths exist for column initialization: (1) `useInvoiceColumns()` no-param + async `setColumns` (EditInvoice, QuotationForm edit), (2) `useInvoiceColumns()` no-param only (NewInvoice, QuotationForm new, with optional prefill effect), (3) direct DB read bypassing hook (view/preview/PDF paths)
